# Fetch a scene preview

An ordinary scene preview continues to use verified bytes already on disk. When those exact target bytes are missing, a supported Windows companion engine can briefly request them from the same torrent. The viewer chooses Fetch preview and stays on the current video.

1. Offer the action after an ordinary preview identifies missing target data and receives a positive capability response from the paired scheduler. Pairing requires the exact configured HTTPS `127.0.0.1` origin with a non-default port and a dedicated leaf certificate pinned by SHA-256. Every new TLS connection verifies the IP SAN, certificate chain and pin before sending credentials. TLS session caching and HTTP redirects are disabled for the paired endpoint. The process receives `CINEMA_SCENE_ORIGIN`, `CINEMA_SCENE_KEY` and `CINEMA_SCENE_CERT_FILE` from its launcher. Credentials and daemon response bodies stay server-side. Ordinary traffic on the paired connection omits the scheduler key and Basic header. Stock, unpaired and converted playback keep their read-only previews.
2. Request a lease only for the same current direct MP4 attachment while the browser plays at 1x with at least eleven seconds in its continuous buffered interval. The server rejects samples more than 500 ms old on delivery and advances the playhead bound at 1x from capture. Independently derive an audio and video byte range for the next twelve seconds from the authenticated MP4 sample tables, including preceding random access, audio preroll and decode reorder. Align outward to two through 64 full, verified torrent pieces within the file. The opening index remains verified separately. At native dispatch reject samples older than two seconds and recompute runway from capture. The smaller of browser and verified media runway must still cover the six-second lease plus a four-second margin, which can shorten the window further. The lease targets only missing pieces outside the reserve, within the engine's 16-piece and 8 MiB limits.
3. Bind the request to the active playback ticket, app connection epoch, selection generation, file identity and captured qBittorrent session. Bound the grant response to 1,250 ms. Recheck the reserve, projected runway and attachment between status checks with a 150 ms delay and a 750 ms status-call limit. Stop on pause, seek, rate change, playback interruption, ended or hidden state, depleted reserve, attachment change, completion, or expiry. Send at most one best-effort cancel for the captured ID on the still-current paired connection, bounded to 750 ms. If the request response is lost, the engine's own six-second deadline bounds the unknown lease. Never replay it. Before presenting the clip, independently hash the returned target pieces and revalidate the file identity.
4. Exercise an isolated Windows companion and actual WebView2 on synthetic incomplete media with a bounded transfer rate. The main media URL and playback ticket must stay identical and media time must advance by at least 80% of elapsed time through a successful preview with no waiting event. Record the minimum continuous browser buffer and target completion time. Verify the rendered preview frame against the independent source and match picture frames and decoded PCM from the received target pieces against the source fixture.

   - Verify stock fallback, the browser buffer floor, stale samples at both delivery and dispatch, verified reserve loss, target overlap, modified pieces and stale file identity.
   - Exercise pause, seek, stalled playback, waiting, rate change, error, ended, emptied, attachment changes, and hidden or closed player. A pending browser request must stop. For a known native lease, verify cleanup uses only its captured ID and current pairing. Check cancellation during grant, rejected cleanup, native expiry and no replay after a lost response.
   - Verify scheduler secrets are absent from ordinary requests. Verify redirect refusal, wrong or missing certificate identity, and same-port substitution with a wrong leaf signed by a trusted chain. Check new TLS sockets do not resume a previous session.

Keep the real Windows profile and downloads isolated. Activation on the installed profile requires a separate tested provisioning path.
